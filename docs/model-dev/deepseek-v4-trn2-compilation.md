# Compile DeepSeek-V4 on Trn2

> **Q512/131K handoff (2026-08-26):** The current real-weight TP2/LNC2 cold
> compile exhausts a 124 GiB host because the paged MLA kernels statically
> expand the query axis and still materialize query-by-history latent and
> probability tensors. See
> [DeepSeek-V4 Q512 MLA compiler graph explosion](deepseek-v4-q512-mla-compile-explosion.md)
> for the reproduction, artifact evidence, and implementation acceptance gate,
> and the
> [development environment handoff](deepseek-v4-development-environment-handoff.md)
> for the exact Native/XLA stacks, paths, cache discipline, and test workflow.

This guide compiles the repository's structurally faithful, tiny DeepSeek-V4
configuration through the real vLLM Neuron path:

```text
PyTorch graph capture -> HLO -> neuronx-cc at O1 -> NEFF -> device warmup
```

It is the fastest end-to-end compilation check for changes under
`vllm_neuron/model/deepseek_v4/`. It uses a real, randomly initialized
Safetensors checkpoint generated by
`test/vllm_neuron/test_deepseek_v4_device_e2e.py` and captures three graphs:

- prefill with 8 tokens;
- prefill with 64 tokens;
- decode with shape `(batch=1, sequence=64)`.

This is **not** a claim that the full DeepSeek-V4 checkpoint is ready for
production. In particular, the tiny model currently emits Neuron runtime
scatter/gather out-of-bounds notifications during warmup. Compilation and cache
lifecycle are green; device numerical correctness is still under investigation.

## Validation result: 2026-08-21

The publication correctness gate is **not green** on the repository's
`trn2.3xlarge` development instance. The padding-aware compressed-cache fix
passes the CPU correctness suites, and the cold Trn2 run compiled all three
requested graphs and generated four in-range tokens, but Neuron runtime
notifications make the device run a failure even though the process exited
successfully.

The isolated-cache TP1/O1 run produced:

| Target/stage | Cache key | Result |
| --- | --- | --- |
| Decode `(1,64)` | `0d435021887b05d515c462b4a73a1e8a` | compiled in 25.1s; out-of-bounds notifications |
| Prefill 8 | `cd57d45bf690aec8abf10247f4befb24` | compiled in 71.9s; warmup clean |
| Prefill 64 | `9ff77ad7f1524aa87c9bc77e75faa0a3` | compiled in 834.8s; out-of-bounds notifications |
| Parallel trace | all three | 178.8s |
| Engine initialization | all three | 1057.5s |
| Generation | prompt 8, four tokens | completed, but invalidated by notifications |

The runtime reported vector-DGE scatter/gather out-of-bounds access for
prefill-64 and vector- plus scalar-DGE out-of-bounds access for decode. The
engine still logged warmup success and exited zero, confirming that validation
must scan captured subprocess output rather than trust process status alone.

Shutdown independently reproduced:

```text
RuntimeError: device_allocator INTERNAL ASSERT FAILED at
CachingDeviceAllocator.h:252. Allocator for neuron is not a DeviceAllocator.
```

A restart/cache-reuse run was not accepted because the cold run already failed
the notification gate. The three completed entries remain available for
diagnosis. Do not publish this as a clean correctness result until the accesses
are fixed and a restart proves three cache hits with zero submitted HLOs.

## Hardware choices

The procedure was verified on this repository's `trn2.3xlarge` development
instance. Use it there when validating graph capture, compiler compatibility,
or a small model-code change.

A `trn2.48xlarge` is the practical next step when validating larger tensor
parallel configurations or a real checkpoint. The tiny TP1 test itself does not
need the larger instance. Always use `neuron-ls` to discover the devices exposed
to the host or container instead of copying a device range from another machine.

AWS recommends a current Neuron Deep Learning AMI and local NVMe storage for
compiler caches. See the official [vLLM Neuron setup
guide](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/vllm-neuron/docs/getting-started/setup-guide.html)
and [Neuron multi-framework DLAMI
guide](https://awsdocs-neuron.readthedocs-hosted.com/en/v2.32.0/setup/multiframework-dlami.html).

## 1. Prepare the checkout and environment

Start from the branch containing the DeepSeek-V4 and stale-HLO fixes:

```bash
git checkout deepseek-V4-on-0.24
git status --short
```

Activate the repository environment. The commands below assume `.venv`; adjust
the path if the Neuron DLAMI environment has a different name.

```bash
source .venv/bin/activate
python -m pip install -e .
python -m pip install -r requirements/test.txt
```

Verify the runtime and compiler before reserving device time:

```bash
neuron-ls
command -v neuronx-cc
neuronx-cc --version
python - <<'PY'
import torch
import vllm
import libtorch_neuronx_lite

from libtorch_neuronx_lite.compile.platform import get_platform_target

print("torch:", torch.__version__)
print("vllm:", vllm.__version__)
print("libtorch-neuronx-lite:", libtorch_neuronx_lite.__file__)
print("target:", get_platform_target())
PY
```

`command -v neuronx-cc` must succeed in the same shell that launches vLLM. A
common failure mode is invoking `.venv/bin/python` without activating the
environment: the Python package imports, but child engine processes cannot find
the `.venv/bin/neuronx-cc` launcher. Either activate the environment or prepend
its absolute `bin` directory to `PATH`.

## 2. Choose an isolated local compiler cache

Do not point an experimental compile at a shared or production cache. Use fast
local storage:

```bash
export VLLM_CACHE_ROOT=/tmp/vllm-neuron-deepseek-v4-compile
mkdir -p "$VLLM_CACHE_ROOT"
```

The Neuron compile cache will be created below:

```text
$VLLM_CACHE_ROOT/neuron/compile_cache
```

Do not delete incomplete hash directories to recover from a failed process. On
the next launch, the worker moves an incomplete capture owned by the same server
prefix and TP rank under:

```text
<cache-key>/.incomplete_hlo_quarantine/
```

The old HLO, FX graph, command, metadata, and compiler logs remain available,
but `parallel_compile()` cannot rediscover them.

## 3. Set the device environment

For the small instance and TP1 test:

```bash
export NEURON_VISIBLE_DEVICES=0
export VLLM_NEURON_ENABLE_DEEPSEEK_V4=1
unset VLLM_NEURON_CPU_MODE
unset VLLM_NEURON_CPU_COMPILE
```

If the instance or container has no EFA interface, disable only the optional CPU
affinity optimization:

```bash
export NEURON_SKIP_EFA_AFFINITY=1
```

This is the runtime-recommended workaround for an absent EFA device; it does not
disable Neuron compilation or execution. Leave it unset when EFA is installed
and visible.

If the virtual environment was not activated, explicitly repair `PATH`:

```bash
export PATH="$(pwd)/.venv/bin:$PATH"
```

Confirm once more:

```bash
command -v neuronx-cc
neuron-ls
```

## 4. Run the real tiny-model compilation

The device E2E module is normally pytest-skipped unless CPU mode is selected.
For a real device compile, invoke its checkpoint builder and runner directly:

```bash
python - <<'PY'
import runpy

test_module = runpy.run_path(
    "test/vllm_neuron/test_deepseek_v4_device_e2e.py"
)
test_module["_run"](tensor_parallel_size=1)
print("TINY_DEVICE_COMPILE_AND_GENERATE_OK")
PY
```

Do not set `VLLM_NEURON_CPU_MODE=1` for this command. The tiny checkpoint uses:

- hidden size 32;
- three attention variants/layers;
- vocabulary size 64;
- maximum model length 64;
- prefill buckets `[8, 64]`;
- decode target `(1,64)`;
- tensor parallel size 1;
- compiler optimization level O1, selected by the Neuron platform default.

## 5. Recognize a successful compile

Expected graph-extraction messages include:

```text
Extracting graphs for 2 prefill buckets: [(8, 0), (64, 0)]
Extracting 1 decode compile targets: [(1, 64)]
Parallel trace: jobs=3, lanes=3
```

The compiler must receive exactly the current three HLOs:

```text
rank 0: compile — 3 total HLOs, 3 assigned to this rank
```

Success requires all three `Compiled HLO ...` messages followed by local cache
hits during warmup. Inspect the durable result with:

```bash
find "$VLLM_CACHE_ROOT/neuron/compile_cache" -maxdepth 2 -type f \
  \( -name '*.neff' -o -name '.compilation_complete' \) -print
```

There should be three NEFFs and three completion markers. On the verified
`trn2.3xlarge` run, approximate cold timings were:

| Stage | Time |
| --- | ---: |
| Parallel trace, three graphs | 176 seconds |
| Smallest graph compilation | 23 seconds |
| Medium graph compilation | 70 seconds |
| Prefill-64 compilation | 788 seconds |
| Engine initialization including compilation | 1,008 seconds |

These are diagnostic observations, not performance guarantees. Compiler time
varies with SDK version, host contention, and compiler worker settings.

## 5a. Where the time actually goes, and how to cut it

The three graphs compile in parallel, so the wall clock is the longest single
compile, not the sum. A second cold run measured:

| Stage | Time |
| --- | ---: |
| Weight loading | 0.01 seconds |
| Parallel trace, three graphs, three lanes | 132 seconds |
| Decode `(1,64)` compilation | 24 seconds |
| Prefill-8 compilation | 72 seconds |
| Prefill-64 compilation | 689 seconds |
| Warmup and device load | 47 seconds |
| Total | about 870 seconds |

Prefill-64 alone is roughly 80 percent of a cold start. Everything else,
including the compiler flags and the worker-pool settings, is noise against it.

`neuronx-cc` is not slow here in general: a 22-layer TinyLlama compiles in about
80 seconds on the same host. The prefill-64 graph is slow because it is large,
and it grows linearly with sequence length:

| Captured FX graph | Decode, 1 token | Prefill-8 | Prefill-64 |
| --- | ---: | ---: | ---: |
| Total nodes | 2,637 | 8,475 | 55,179 |
| `torch.arange` | 35 | 280 | 2,240 |
| `einsum` | 12 | 96 | 768 |
| `index_copy` | 11 | 88 | 704 |

That is exactly 35 aranges, 12 einsums, and 11 index_copies per token.
`DeepseekV4Attention.forward` loops over tokens in Python
(`vllm_neuron/model/deepseek_v4/model.py`), and because the bucket size is
static the loop fully unrolls into one complete attention body per token per
layer: 64 by 3 equals 192 bodies in the prefill-64 graph. The module docstring
records this as a deliberate correctness-first choice, and it is genuinely
required only for the compressed layers, where compression boundaries are
positional.

Two levers follow directly, and the launcher exposes both behind
`VLLM_NEURON_TINY_FAST=1`:

```bash
VLLM_NEURON_TINY_FAST=1 tools/deepseek_v4/run_tiny_tp1.sh \
  /tmp/deepseek-v4-tiny /tmp/deepseek-v4-fast-cache 8001
```

* `--max-model-len 16` instead of 64, with buckets `[8,16]`. Fewer unrolled
  token bodies. `deepseek-v4-tiny-tp1-neuron-investigation.md` measures graph
  extraction dropping from about 218 seconds to about 29, and the whole
  compile-and-run cycle from roughly 16 minutes to about 3, and records that
  length 16 still reproduced the original fourth-token mismatch exactly.
* `--num-gpu-blocks-override 32` instead of 256. `scatter_paged_latent` builds
  a `torch.where` over the entire cache once per token, and capacity is
  `num_blocks * storage_block_size`, so 256 blocks means a `[32768, latent]`
  intermediate per token for the MLA group while serving 64 tokens. The floor is
  the largest value in the runner's logged
  `max_num_blocks_per_req=[1, 2, 2, 2, 8, 16]` plus a null block; re-read that
  log line before lowering it further.

`tools/deepseek_v4/generate_tiny_tp1.py` takes `--max-model-len` and
`--num-gpu-blocks-override` directly, with the gate values as defaults.

Measured on `trn2.3xlarge`, cold, with an empty isolated cache root:

| Stage | Gate profile | Fast profile |
| --- | ---: | ---: |
| Parallel trace, three graphs | 132 seconds | 29 seconds |
| Decode compilation | 24 seconds | 27 seconds |
| Prefill-8 compilation | 72 seconds | 71 seconds |
| Longest prefill compilation | 689 seconds | 126 seconds |
| Total, launch to warmup complete | about 870 seconds | 196 seconds |

Both profiles emit three NEFFs and generate four valid tokens. Captured graph
sizes track the compile times: 2,591 nodes for decode, 8,429 for prefill-8, and
15,101 for prefill-16, against 55,179 for prefill-64.

Note which lever does what. The length reduction is what shrinks the node count
and therefore the compile time; the block-count reduction leaves the node count
almost unchanged (8,429 versus 8,475 for prefill-8) because it shrinks the
*volume* of each scatter intermediate, not the number of operations. Keep both,
but do not expect the block override alone to move the wall clock much.

The fast profile is opt-in on purpose. The accepted-run signature in Step 5
is defined against the default values, so a plain invocation must keep
producing exactly three NEFFs at length 64.

Two further points worth knowing before spending device time:

* Most model-code questions never need `neuronx-cc` at all. Shape and Dynamo
  blockers reproduce on CPU through the tracing-proxy pattern in
  `tools/deepseek_v4/check_carry_rows_dynamo_trace.py`; numerics reproduce under
  `VLLM_NEURON_CPU_MODE=1 ... --enforce-eager`, which skips warmup and NEFF
  generation outright. When only decode matters,
  `VLLM_NEURON_SKIP_PREFILL_WARMUP=1` drops the expensive graph entirely.
* Do not reach for compiler flags. `-O1` is already the Neuron default and is
  the fastest level, the trace and compile pools already exceed the three
  available jobs, and any change to the compiler arguments, including
  `--verbose`, is part of the cache key and invalidates every existing entry.
  Enabling tensor capture changes the FX graph and voids the cache the same way.

## 6. Validate cache reuse with a second launch

Run the command from Step 4 again without changing the model configuration,
compiler options, SDK, target, or cache root. Completed entries must remain in
place. Warmup should report local cache hits for the same three keys.

If the previous process died before writing `.compilation_complete`, expect one
quarantine log per incomplete key before extraction. `parallel_compile()` must
still report only three submitted HLOs, not six.

Useful inspection commands:

```bash
find "$VLLM_CACHE_ROOT/neuron/compile_cache" \
  -path '*/.incomplete_hlo_quarantine/*/graph.hlo' -print

find "$VLLM_CACHE_ROOT/neuron/compile_cache" -maxdepth 2 \
  -name '.compilation_complete' -print
```

## 7. Moving to a larger Trn2 instance

On `trn2.48xlarge`:

1. Put `VLLM_CACHE_ROOT` on local NVMe, not NFS or a shared home directory.
2. Use `neuron-ls` to determine the visible device IDs.
3. Keep the tiny smoke test at TP1 first. It provides a direct comparison with
   the known `trn2.3xlarge` result.
4. Increase `tensor_parallel_size` only when testing a checkpoint/configuration
   that requires it, and expose a matching device set.
5. Use a distinct cache root for every compiler-option, SDK, hardware-target, or
   experimental model change unless deliberate cache reuse is under test.

The repository's other Trn2 recipes commonly use TP16 for large models, but the
correct TP degree for the full DeepSeek-V4 checkpoint must be established from
its weight memory, KV-cache budget, and supported parallel layers. Do not infer
full-checkpoint readiness from this TP1 tiny-model compile.

## Troubleshooting

### `neuronx-cc compiler binary does not exist`

The engine subprocess cannot resolve the compiler launcher. Activate the virtual
environment or export its absolute `bin` path:

```bash
export PATH="$(pwd)/.venv/bin:$PATH"
command -v neuronx-cc
```

### `No EFA device found .../infiniband`

If EFA is intentionally absent:

```bash
export NEURON_SKIP_EFA_AFFINITY=1
```

If EFA should exist, fix the host/container device exposure rather than using
the workaround.

### More HLOs are submitted than expected

Confirm that the stale-HLO quarantine fix is present and that the worker logs a
quarantine location for each abandoned capture. Do not globally clear the cache;
preserve the old HLO and compiler log for diagnosis.

### Runtime scatter/gather out-of-bounds notifications

Compilation may still produce valid NEFF files and completion markers, but the
run is not a correctness pass. Preserve the cache and Neuron runtime logs. The
current investigation should focus on heterogeneous KV-cache allocation, block
tables, slot mappings, and padded page bounds.

### Allocator assertion during engine shutdown

The current environment can report that the Neuron allocator is not a PyTorch
`DeviceAllocator` during teardown. Record it separately from the compilation
result; do not let it hide earlier compiler or runtime failures.
